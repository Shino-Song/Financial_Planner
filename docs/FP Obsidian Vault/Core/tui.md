The TUI will be a curses and/or urwid based Text User Interface to give users the option to run in a terminal rather than a dedicated GUI. I am exploring both curses and urwid to better understand each system and see the benefits and drawbacks of each.

First up we have the curses system. This interface will use the curses module with python to create a set of necessary boxed zones that display necessary information as follows -

1. The "outer limits" zone. This marks the entirety of the given terminal space and provides a visual boarder for a primary asthetic show of the application's visual boundaries within the terminal.
2. The UID. This zone will dispaly the User's ID, be it an individual's name, the company they work for, their position, etc... This will be changeable at any time, but will be reflected on any reports. For any visual anonymity needs, a pseudonym can be provided, which will change the displayed name on the active session, but provide the actual name in any reports.
3. Active item/menu. This is zone displays the name of the active item/menu being obsered and any relevant information. For example, if the user is in a menu this zone will display the menu name. If the user is in a financial sheet, it will display the given financial sheet (eg. 2024 - expenses - Utilities).
4. The lanky boy. For lack of a better catchall name, this zone has multiple purposes based on the context of the type of screen one is interacting with. If the user is in a report screen, it will display a truncated itemization of transactions with a total at the bottom (long sum and difference math problem) and displaying expenses and incomes in relevant colors for easy visual identification. If the user is in a menu, it will show relevant information of the menu, such as menu paths, files/database options, etc...
5. Main infobox. This zone is also vairable based on the context of the type of interaction being had. For example, if the user is accessing a menu, it will be the primary display of questions, text history, and other general information needing to be displayed. If the user is in a budget sheet, it will give greater details and visualizations of the line items than the Lanky Boy zone. Overall, it is the primary zone that the user will be looking at for any information and prompts.
6. User Input Zone. This zone is for the user's text input. All interactions will be primarily done as text input, as such, a zone to see the user's text input is necessary. For this, it will be a single typable line that spans across 3 lines above the bottom of the of the terminal.
7. Date/time. Simple date time.

For this interface, a key problem will be natural and intuitive interaction as well as clear display of important information. This is not a "bells and whistles" interface, but it certainly won't be an ugly or painful to one. The purpose of this interface is a last resort for the user when nothing else is working.

Other problems to solve -

1. Scalable resoltion/terminal size. As the interface will crash if outside the bounds of a terminal's capabilities, this terminal will need to be scalable. This is also to address a visual aspect as a fix "minimum resolution" will result in unecessarily small interfaces as well. For this, I will be developing a funtion to call for the terminal's current resolution and then change the zone coordinates based on that information. Certain aspects will necessarily be fixed, such as zone height of the UID, Active Item/Menu, and User Input Zones, as those will need to be 3 lines tall (2 lines for the rectangle boarder, and 1 line for the text). All viriable aspects of the resolution will adjust as necessary to the given terminal resolution. Points to note for this problem.
    1. Users changing the size of a terminal window. As a user can manually change the size of a monitor, be it intentional or accidental, it would be inconvenient for the interface to crash, likely losing all data progress (temporary recall states to be addressed later). For this, a solution will need to be developed to actively get the resolution of the temrinal and adjust the zones accordingly. Some solution for items going past the immediate boundaries will need to be added as well, as I imagine that in the time it takes for the program to notice a change, update the resolution, and then adjust the items will be too long and crash the program before any actions could have been taken.
    2. removal of windows if resolution is too small. While I doubt there will ever be a situation where the resolution of a terminal is "too small" to fit all the relevant elements, I believe it would be best to plan for it's happening as a just in case. Better safe than sorry for extreme cases. For this, I will be having zones split into "vital" and "optional" based on whether they are absolutely necessary for operation, or can be considered for removal should terminal resolutions get below a certain size.
With these situations considered, it will hopefully avoid any crashes in the situation where terminals are resized or are inherently too small to incorporate every general visual I would otherwise plan on in a typical use case scenario.
